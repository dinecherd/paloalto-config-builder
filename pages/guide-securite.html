    Les 3 types de règles et les règles par défaut

    Une règle de sécurité compare une session à des critères (zones, adresses, utilisateur, application, service, URL) puis applique une action : allow, deny, drop ou reset.

    🔁 intrazone

    Trafic à l'intérieur d'une même zone (source zone = destination zone). Ex. Users_Net → Users_Net.

    ↔️ interzone

    Trafic entre zones différentes uniquement. Ex. Users_Net → Internet.

    🌐 universal défaut

    Type par défaut d'une nouvelle règle (onglet General › Rule Type) : s'applique à l'intrazone ET à l'interzone pour les zones listées.

    Les deux règles prédéfinies (toujours en bas de la base de règles)

    NameTypeSource ZoneDestination ZoneApplicationServiceActionLog

    2intrazone-defaultintrazoneany(intrazone)anyanyAllow— non loggé
    3interzone-defaultinterzoneanyanyanyanyDeny— non loggé

    Capture simulée — état après la première règle du Lab 6

    intrazone-default → AllowPar défaut, le firewall autorise implicitement le trafic à l'intérieur d'une même zone.
    interzone-default → DenyTout trafic entre deux zones différentes est refusé tant qu'aucune règle explicite ne l'autorise.
    Pourquoi mon ping vers 8.8.8.8 n'apparaît-il pas dans le Traffic log ?
    C'est la question piège du Lab 6. Deux raisons : (1) aucune règle n'autorise encore Users_Net → Internet, donc la session tombe sur interzone-default (deny) ; (2) les règles prédéfinies ne journalisent pas par défaut, alors que les règles personnalisées journalisent par défaut (Log at Session End). Pour voir ces refus : sélectionner interzone-default sans l'ouvrir → bouton Override → onglet Actions → cocher Log at Session End → OK → Commit.

    Rule shadowing (règle masquée)Si une règle large est placée au-dessus d'une règle plus précise, celle-ci ne sera jamais atteinte. Au commit, l'onglet Rule Shadow de la fenêtre Commit Status signale les règles masquées : réordonnez-les (Move / glisser-déposer) ou affinez-les.

    Où se place la politique de sécurité dans le traitement d'un paquet

    1. Session existante ?Si oui → traitement rapide (fast path).
    2. Zone sourceDéterminée par l'interface d'entrée. Zone / DoS Protection.
    3. Forwarding lookupPBF puis table de routage.
    4. Zone destination+ vérification DNAT (politique NAT évaluée).
    5. Security Policy checkSur les IP pré-NAT (App-ID encore ignoré) → ID de session.
    6. App-ID / Content-IDIdentification de l'application, inspection.
    7. EnforcementSecurity Policy (avec App-ID) + Security Profiles.
    8. ForwardNAT appliqué, paquet transmis.
    Pourquoi deux contrôles de la politique de sécurité ?
    Au premier paquet, l'application n'est pas encore connue : le firewall vérifie qu'une règle peut correspondre sur les critères réseau (zones, IP pré-NAT, port) et crée la session. Une fois l'application identifiée par App-ID, la politique est réévaluée avec l'application réelle, puis les Security Profiles (Content-ID) sont appliqués. Une session = un flux client→serveur (c2s) qu'une règle doit autoriser ; le flux retour (s2c) est autorisé automatiquement.
    03

    Les briques : objets, services, applications

    Une règle lisible réutilise des objets plutôt que des IP en dur. On les crée dans l'onglet Objects avant de construire la règle.

    📍 Address / Address Group

    Objects › Addresses › Add : IP Netmask, IP Range, IP Wildcard Mask ou FQDN.

    • Static Address Group : membres ajoutés à la main, commit nécessaire.
    • Dynamic Address Group : membres ajoutés via des tags, sans commit.
    • Les External Dynamic Lists prédéfinies (ex. Palo Alto Networks – Known malicious IP addresses) s'utilisent comme des adresses.

    🔌 Service

    Objects › Services › Add : protocole TCP/UDP + port(s) de destination.

    • Seuls service-http (TCP 80, 8080) et service-https (TCP 443) sont prédéfinis.
    • any = tous les ports. À éviter sur une règle allow.

    🧩 Application (App-ID)

    Onglet Application : Any par défaut. En production, listez les applications réelles (ex. web-browsing, ssl, dns) et ajoutez leurs dépendances : le commit signale les dépendances non résolues.

    🎯 application-default

    Valeur par défaut du champ Service. L'application n'est autorisée que sur ses ports standards : web-browsing sur TCP 80, ssl sur TCP 443. Bloque l'évasion de port (une appli légitime sur un port exotique).

    🏷️ Tags

    Objects › Tags › Add : couleur + nom. Sur les règles et objets, pour filtrer, repérer visuellement et regrouper (Group Rules By Tag / vue par groupes de tags), sans changer la priorité des règles.

    🕒 Schedules

    Objects › Schedules › Add (format 24 h : quotidien, jours de semaine, dates), puis appliqué dans l'onglet Actions › Schedule de la règle.

    Security Profiles, logging, hit count & Policy Optimizer

    Une règle allow n'est qu'une porte ouverte. Ce qui la rend sûre : les profils de sécurité et la visibilité (logs, compteurs).

    ÉlémentOù ?À retenir
    Security ProfilesRègle › Actions › Profile SettingProfile Type Profiles (Antivirus, Anti-Spyware, Vulnerability Protection, URL Filtering, File Blocking, WildFire Analysis) ou Group. Appliqués uniquement au trafic autorisé.
    Log at Session EndRègle › Actions › Log SettingCoché par défaut sur les règles personnalisées, pas sur intrazone/interzone-default.

    Pourquoi vérifier le routage avant la règle ?
    La zone de destination d'une session est déterminée par le lookup de routage : 8.8.8.8 correspond à la route par défaut 0.0.0.0/0 via ethernet1/1, donc la zone de destination est Internet. Si la route manque, aucune règle « → Internet » ne pourra jamais correspondre.

    ✗ À ne pas faire / ✓ À faire

    Le comparatif à garder en tête avant chaque commit.

    ✗ À ne pas faire✓ À faire
    Règle any → any, application any, service any, allow.
    Zones précises, objets d'adresse, applications réelles : principe du moindre privilège.
    Service any sur une règle allow (évasion de port possible).
    application-default sur les allow ; any sur les règles deny.
    Une règle large en haut qui masque les règles précises en dessous.
    Blocages en haut, puis du plus spécifique au plus général ; lire l'onglet Rule Shadow.
    Créer une règle de blocage en oubliant l'onglet Actions (reste en Allow).
    Toujours relire l'onglet Actions avant OK.
    Allow sans profil de sécurité, sans description ni tag.
    Profile Group sur chaque allow, Description, Tags, Audit Comment.
    Désactiver les logs, laisser s'accumuler des règles mortes.
    Log at Session End, logging de interzone-default, nettoyage via Hit Count et Policy Optimizer › Rule Usage.

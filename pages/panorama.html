Comprendre Panorama

Les 4 concepts à maîtriser avant de configurer.

🧱Template / Template stack

Onglets Network et Device : tout ce qui fait « tourner » le pare-feu. Plusieurs templates sont empilés dans un template stack, auquel on rattache les pare-feux.

  • Interfaces, zones, virtual routers, VPN
  • DNS, NTP, fuseau, bannière, syslog
  • Administrateurs locaux, profils serveurs

🗂️Device group

Onglets Policies et Objects : ce que le pare-feu autorise ou bloque. Les device groups forment une hiérarchie sous Shared (jusqu'à 4 niveaux).

  • Règles de sécurité, NAT, décryptage, PBF
  • Objets adresses, services, applications, tags
  • Profils de sécurité, log forwarding profiles

Du haut vers le bas, première règle qui matche

Le pare-feu évalue un ensemble unique de règles : les pre-rules poussées par Panorama passent avant les règles locales, les post-rules après. Pour les pre-rules, Shared puis parent puis enfant ; pour les post-rules, l'ordre s'inverse (enfant, parent, Shared).

1. Clique la couche qui contient la règle correspondant au flux. 2. Envoie un paquet.

Astuce : les pre-rules servent aux règles imposées (blocages globaux), les post-rules aux règles « filet » avant le deny par défaut. Un admin local ne peut pas modifier les règles poussées par Panorama.

Device groups : l'héritage descend

Clique un niveau pour y créer l'objet addr-DNS-Interne : il est visible dans ce device group et tous ses descendants, jamais chez les parents ni les frères.

Template stack : le plus haut gagne

Pour chaque paramètre, le pare-feu reçoit la valeur du template le plus haut du stack qui la définit. Les variables $ permettent ensuite une valeur différente par pare-feu.

Deux étapes : enregistrer sur Panorama, puis pousser

Un Commit to Panorama valide la configuration candidate dans la running config de Panorama — rien ne change encore sur les pare-feux. Le Push to Devices envoie device groups et template stacks aux pare-feux choisis (portée « Edit Selections »). Commit and Push enchaîne les deux.
